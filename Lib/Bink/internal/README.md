# In-tree Bink 1 decoder

This directory replaces RAD's `binkw32.dll` with a decoder compiled into
`ma_win.exe`. It is a C++ port of [unbikit
0.10.7](https://github.com/blennies/unbikit) (MIT OR Apache-2.0),
specialised to the 39 movies in the retail Xbox data set:

- Bink 1 revision `i`; no Bink 2.
- 4:2:0 YUV, limited range, no alpha, no scaling/interlace flags.
- Stereo Bink Audio DCT at 22.05 kHz or 44.1 kHz; three loading/license movies
  have no audio.

`LICENSE-unbikit.md` is the upstream license and must stay with the source.

## Backend selection

`MA_BINK_BACKEND` is a CMake cache option:

- `internal` (default since R149): compiles this directory into a static
  `bink_internal` library, links it into `ma_win`, and defines `__RADINEXE__`
  for `fang2win`, `ma_win`, and the decoder. The executable no longer imports
  `binkw32.dll`.
- `external` (fallback): links `Lib/Bink/binkw32.lib` exactly as before. The
  game imports `binkw32.dll`, so the retail RAD DLL or the FFmpeg shim can be
  swapped at runtime without rebuilding.

The internal path was exercised under Wine before becoming the default:
loading screens, 44.1 kHz campaign intros, 22.05 kHz startup logos, and the
audio/pause/volume paths. Native Windows reports are welcome. R148's validated
external package remains available.

Example builds (the existing `build_o2` cache already has the toolchain,
`MA_WINGC=ON`, and -O2):

```sh
. tools/env.sh
# The default is internal; this is also the shipping build.
cmake -S orig/ma -B build_o2 -DMA_BINK_BACKEND=internal
cmake --build build_o2 -j8

# External fallback (uses binkw32.dll):
cmake -S orig/ma -B build_ext \
      -DCMAKE_TOOLCHAIN_FILE=$PWD/orig/ma/cmake/toolchain-mingw-i686.cmake \
      -DMA_BINK_BACKEND=external -DMA_WINGC=ON
cmake --build build_ext -j8
```

Verify the switch:

```sh
i686-w64-mingw32-objdump -p build_o2/ma_win.exe  | grep -i binkw32   # no match
i686-w64-mingw32-objdump -p build_ext/ma_win.exe | grep -i binkw32   # found
i686-w64-mingw32-nm build_o2/ma_win.exe | grep _BinkOpen@8           # defined
```

An internal build may still find a `binkw32.dll` next to the executable; it is
simply not imported. `make_release.py` would need to stop copying the DLL only
when the package is built from an internal build directory.

## Files

| File | Purpose |
|---|---|
| `bink_bits.h` | LSB-first bit reader matching unbikit's read-past-end semantics. |
| `bink_tables.{h,cpp}`, `bink_tables_data.h` | Huffman/pattern/quant/audio tables. The header is generated by `tools/bink/gen_tables.py` from the upstream source; do not hand-edit it. |
| `bink_idct.{h,cpp}` | Integer AAN IDCT and block add/put. |
| `bink_video.{h,cpp}` | Frame/plane decoder (scaled, motion, run, residue, intra, fill, inter, pattern, raw blocks). |
| `bink_dct.{h,cpp}` | Recursive inverse DCT used by Bink Audio. |
| `bink_audio.{h,cpp}` | Bink Audio DCT decoder, overlap window, float blocks. |
| `bink_decoder.{h,cpp}` | 44-byte header, audio-track headers, frame index, frame/audio packet iteration, loop reset. |
| `bink_internal_abi.cpp` | The 14 imported stdcall functions, read-only file mapping, DirectSound ring, timing, YUV -> surface conversion. |

The engine-facing header remains `Lib/Bink/bink.h`. The private `Movie` context
starts with the public 16-byte `Width/Height/Frames/FrameNum` prefix; the engine
reads no other `HBINK` fields.

## Validation

The host-side probe is `tools/bink/binkprobe` (build with
`make -C tools/bink`). It decodes the same source files as the game build.

### Video

Compared with FFmpeg 7.0.2, all 39 movies:

- 3 full streams are bit-exact: `xb_Loading.bik`, `xb_Loading2.bik`,
  `xb_license.bik`.
- The other 36 full streams differ only by **±1 on 1-12 luma pixels** at the
  first differing frame. All 36 first differences were checked with
  `tools/bink/compare_frame.sh`; none were structural. The difference is
  integer IDCT rounding, not a bitstream/parser error.
- Decode speed on the development host: ~1,100 fps at 640x480 (500-frame
  benchmark) and ~6,500 fps at 640x320. The game needs 30 fps.

The 620x340 loading movie is decoded correctly; unbikit's own
`stride*7` row advance is wrong for it, which is why this port uses padded
32-aligned strides and explicit row origins.

### Audio

Compared with FFmpeg 7.0.2 over every audio movie:

- All 36 audio movies have **exact sample counts** (`ff == ma` for every file).
- Maximum absolute sample difference is **≤5 LSB**; mean difference is below
  0.016. Examples: `xb_intro$.bik` (44.1 kHz, 25,973,760 samples) max 3;
  `xb_finale$.bik` (22.05 kHz, 8,536,320 samples) max 3; `xb_SAS_Logo.bik`
  max 5.
- Both 22.05 kHz (`frameLen=1024`) and 44.1 kHz (`frameLen=2048`) are covered.

The port applies `2 * baseQuant * (1024 / frameLen)^1.5` after the IDCT.
unbikit's `4 * baseQuant` is 2x too loud at 1024 and 4*sqrt(2)x too loud at
2048 relative to FFmpeg/RAD; the exponent was measured, not guessed.

### Colour conversion

`BinkCopyToBuffer` converts limited-range BT.601 YUV 4:2:0 to BGRA/RGBA,
RGB565/RGB555, and BGR/RGB24. Against FFmpeg's `yuv420p -> bgra` on
`xb_Loading2.bik`, 133 of 819,200 bytes differ, by at most 2; alpha is exact.

### Build verification

- External: `ma_win.exe` imports `binkw32.dll` and exactly 14 Bink/RAD symbols.
- Internal: `ma_win.exe` imports no `binkw32.dll`; all 14 symbols
  (`_BinkOpen@8` ... `_RADSetMemory@8`) are defined in the executable.

## Deliberate differences from unbikit

1. **Video stride/row origin.** unbikit advances block rows with
   `blockLineIncr = stride * 7`, which assumes the width is a multiple of 8 and
   spills tail pixels for 620x340. This port uses
   `yStride = alignUp(width + 16, 32)`, an 8-aligned height, and an explicit
   row origin per block.
2. **Audio normalization.** See above; the length-dependent `(1024/frameLen)^1.5`
   factor is required for 44.1 kHz files.
3. **Critical-frequency table.** unbikit's packed table stops at 15,500 Hz while
   FFmpeg's has a final 24,500 Hz entry. For these movies the half-sample-rate
   (11,025/22,050 Hz) selects the same 25 bands in both implementations, so the
   missing entry does not change the output. It is left as upstream to avoid
   diverging from the table generator.
4. **RLE length table.** unbikit's values are already scaled by 8 relative to
   FFmpeg's; the port uses the unbikit table directly and matches FFmpeg.

## Malformed and mod movie files

The retail movies are trusted, but the decoder is also fed user/mod `.bik`
files. R152 hardens that path:

- headers are capped at 2048x2048 / 4M pixels, 1,000,000 frames and 16 audio
  tracks; absurd dimensions are rejected before allocating plane buffers
- Huffman-tree symbol maps and lazily decoded parameter buffers are bounds
  checked; malformed counts/runs stop the frame instead of writing past them
- decoder exceptions are converted to `nextFrame` failures, so they cannot
  unwind through the C ABI and terminate the game
- dequantisation uses a wider product (clamped only outside int32) and the
  internal library is built with `-fwrapv`, keeping malformed IDCT inputs
  defined without changing retail pixels

The host fuzz harness (`tools/bink/fuzz_decode.cpp`) mutates/truncates payloads
and the header test mutates dimensions/counts; both run under ASan/UBSan. The
retail validation remains the authority: video/audio comparisons against
FFmpeg are unchanged.

## Debugging

Set `MA_BINK_LOG=1` before launching the game to append open/loop/audio/surface
messages to `bink_internal.log` next to `ma_win.exe`:

```bat
set MA_BINK_LOG=1
ma_win.exe
```

A value other than `1` is treated as a path (relative paths follow the process
cwd, which the game sets to `assets/`, so prefer an absolute path). Leave it
unset, or set it to `0`, to disable the file. The log is opt-in and otherwise
silent. The probe is the faster way to
reproduce a decode problem: `tools/bink/binkprobe info MOVIE` and
`tools/bink/binkprobe hash MOVIE` do not need Windows.

## Limitations

- Build-time backend switch only. Runtime dispatch would require defining the
  14 functions unconditionally and lazily forwarding to an optional
  `binkw32.dll`; it is not implemented.
- Only the 14 imported entry points exist. `BinkGoto`, `BinkCopyToBufferRect`,
  `BinkGetRects`, `BinkGetSummary`, `BinkGetFrameBuffersInfo`,
  `BinkRegisterFrameBuffers`, and the scratch-buffer API are not implemented
  because the executable imports none of them.
- No RDFT audio, alpha plane, scaling, or interlacing. None of the 39 retail
  movies use them; a modded movie that does will be rejected or decoded
  incorrectly.
- The Windows backend maps the file read-only; the portable probe reads the
  whole file. There is no incremental frame reader yet.
- Audio is prefilled by decoding the leading frames once into the 2-second
  DirectSound ring (target 1.5 s) and then rewinding the video decoder. During
  playback the audio for those leading frames is not decoded again, so the
  first written sample after the prefilled range follows on correctly. This
  mirrors the FFmpeg shim and still needs a real Windows run to confirm
  pause/resume and loop behaviour.
- Runtime-tested under Wine with no `binkw32.dll`: loading screens, 44.1 kHz
  campaign intros, and 22.05 kHz startup logos. Native Windows
  (DirectSound/D3D8) reports are still wanted; the external fallback build
  remains available for anyone who needs it.
